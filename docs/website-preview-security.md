# Hosted website content previews

Hosted content is untrusted, even when it arrives through an authenticated operator connection. A website may intentionally contain JavaScript, malicious markup, remote resources, redirects, or arbitrary binary files. The preview must not grant that content any of the GUI's renderer or preload capabilities.

## Source preview boundary

`WebsiteContentPreview` presents UTF-8 source in a read-only Monaco editor with syntax highlighting. Binary content uses a hexadecimal and printable ASCII view. HTML, SVG, XML, JavaScript, CSS, and Markdown remain source text in this view. Language selection only chooses a locally packaged tokenizer; it does not execute the document or load referenced resources. Links, editing, rich hover/completion content, and unnecessary editor services are disabled.

The source component does not insert HTML, use an iframe/webview, create content-derived resource URLs, or open links. URLs stay selectable source text. The operator can still copy source or export files deliberately; files opened outside the GUI are beyond this preview boundary.

The renderer additionally caps source display at 64 KiB of input and hex display at 4 KiB, regardless of the supplied payload size. Nonprinting and bidirectional formatting controls are shown as explicit Unicode escapes in source previews. Invalid UTF-8 falls back to hex. A prefix ending inside a multibyte character omits the incomplete character and visibly identifies truncation. Previewing never changes hosted bytes.

The text editor accepts only complete UTF-8 content of at most 1 MiB, with matching byte-count metadata and no truncation. It preserves a UTF-8 BOM. Missing bytes, binary content, and partial previews cannot become an editable document that might accidentally overwrite the complete file with its prefix. The main process independently enforces import, export, and editor limits and owns filesystem dialogs and network access.

## Rendered preview boundary

The explicit **Rendered preview** action is available for HTML/XHTML and standalone PNG/JPEG content. Main retrieves the requested stored bytes over the existing authenticated connection and verifies their identity, size, and supplied digest. It never visits the hosted listener URL. Rendering happens in a separate native window without an application preload or application IPC identity.

The window has JavaScript, Node integration, webviews, plugins, developer tools, drag-and-drop navigation, and experimental features disabled. Context isolation, process sandboxing, and web security remain enabled. Its session uses a fresh nonpersistent partition with caching disabled. Navigation, redirects, popups, downloads, permission requests, and network requests are denied. A random document URL is served by a main-owned protocol handler only in that preview session. It returns the sanitized document with `no-store`, `nosniff`, `no-referrer`, and a strict CSP response header. The same CSP appears before uploaded markup in a generated document head; the `sandbox` directive is enforced by the response header, since that directive is not supported in a meta policy.

The preview CSP uses `default-src 'none'`, `script-src 'none'`, and sandboxing with no allowances. Inline CSS is allowed only in this isolated preview document. The application renderer's CSP is unchanged. `img-src data:` is limited in practice to the one image tag generated by main for an independently checked standalone raster file; uploaded HTML cannot supply image tags or resource URLs. Fonts, frames, workers, media, objects, forms, and connections are denied.

`buildWebsiteRenderedPreview` parses HTML with parse5 and rebuilds a small allowlist of ordinary document elements and inert attributes. It removes scripts, frames, forms and controls, embeds, SVG/MathML, templates, metadata, base URLs, links to resources, event handlers, URL attributes, and unknown elements. Text and retained attribute values are escaped during serialization. Uploaded CSP and redirect metadata never reach the generated document.

CSS is parsed with CSS-tree. Only common formatting and layout properties, simple selectors, and bounded values/functions survive. URL functions, escaped URL variants, expressions, custom properties, variable references, imports, font rules and other at-rules, attribute/complex selectors, generated content, animation, filters, and absolute/fixed/sticky positioning are dropped. Inline style attributes and embedded style blocks use the same declaration policy. This is a static layout preview: scripts, external stylesheets, web fonts, embedded images, and active documents are intentionally absent, so it does not reproduce every website exactly.

HTML input is capped at 1 MiB before decoding. Parser callbacks enforce a 10,000-node/work limit, 80 open elements, 64 attributes per element, and 8,192 characters per attribute, including attributes adopted from malformed repeated body/html tags. CSS is limited to 64 KiB of source characters, 20,000 tokens, 16 levels of nesting, 2,000 declarations, and 500 rules; unmatched closing tokens cannot reduce the nesting counter below zero. Generated output is capped at 16 MiB. Limit failures reject the rendered preview rather than opening partially checked content.

Standalone PNG/JPEG input is capped at 8 MiB. Main checks signatures and container structure using byte operations, without invoking a native image decoder. Dimensions must be nonzero, at most 4,096 pixels per edge, and at most 8 million pixels total. Animated PNGs, repeated PNG headers, multiple JPEG frames, late JPEG dimension changes, unsupported JPEG markers, and trailing content are rejected. Main generates the data URL itself with the verified MIME type; Chromium decodes it only in the isolated preview renderer. SVG, PDF, GIF, WebP, and other formats remain source/hex only. Image decoder and browser vulnerabilities remain a reason to keep Electron current; sanitization supplements isolation rather than replacing it.

Preview windows close when their owner is destroyed or their backend binding changes. At most one preview per owner and four total are allowed. Closing revokes the protocol document, clears its byte buffer, and clears the disposable session's storage/cache. Sanitized HTML is never inserted into the operator renderer.

## Transfer limits and server behavior

Directory imports skip dot-prefixed subdirectories (such as `.git`) at every depth unless **Include hidden directories** is checked. The checkbox starts unchecked for each import. This uses POSIX-style names only, not filesystem hidden attributes; dot-prefixed files remain included. The explicitly selected root directory is still imported.

Individual imports and exports are bounded at 32 MiB, directory imports at 500 files, and text editing at 1 MiB. The pinned Sliver server includes hosted file bytes even in its website catalog response, while the SDK's inventory channel accepts at most 32 MiB. Before creating a website or uploading content, main computes the predicted encoded catalog size, including replacements and protobuf metadata, and rejects operations exceeding a 31 MiB aggregate budget. This leaves room for server-generated metadata without raising transport ceilings.

Website mutations sharing a GUI backend connection are serialized through their preflight and write steps. Native file dialogs do not hold that queue; selected content is checked again against its pre-dialog identity, digest, size, and MIME type. MIME-only changes do not resend stale size or digest metadata. This budget is a client preflight, not a server transaction. Another operator can change the catalog between checking and uploading, and a directory upload can partially succeed before a server error. Refresh after an error to inspect server state. Catalogs already exceeding the SDK's inventory limit cannot be listed through this GUI; reduce their content through the native console or another administrative client first. The GUI does not silently increase receive limits or retrieve content from a listener URL as a fallback.

Connection identity is checked again after asynchronous operations and native dialogs. Preview/export responses must match the requested website and content path; missing or mismatched bytes are rejected, and a supplied server SHA-256 must match the returned bytes. Export also rechecks content identity and digest after the save dialog. Preview bytes are cleared when dismissed, and main clears transient RPC/import/export buffers after use. Event summaries carry an inventory-change message, never hosted content.

## Verification

Source component/editor tests cover malicious content, safe editor configuration, language selection, malformed UTF-8, Unicode controls, missing bytes, truncation, and byte limits. Editing tests reject partial and inconsistent content.

`website-rendered-preview.test.ts` covers benign HTML and formatting, hostile scripts/resources/forms, malformed namespace and mutation-XSS payloads, URL and expression CSS variants, CSP ordering, parser bounds, malformed CSS nesting, unsupported media, raster signature/dimension checks, APNG and multi-frame JPEG rejection, and output bounds. Window-controller and Electron E2E tests verify the independent window/session, actual rendered content, blocked resources/navigation, disabled JavaScript, and absence of preload APIs.

The design follows Electron's warning about arbitrary untrusted content and keeps its recommended isolation protections intact. See [Electron security guidance](https://www.electronjs.org/docs/latest/tutorial/security/) and [context isolation](https://www.electronjs.org/docs/latest/tutorial/context-isolation).
