# Beacon command protocol and capability matrix (BC-01)

- Pinned Sliver commit: [`f8430cecf7ceb5cb332c84fb36aba9b75188802d`](../protocol/sliver-baseline.json)
- Scope: command-tree rows labeled beacon-visible in the pinned [parity inventory](operator-parity.md)
- Delivery boundary: this assessment does not add a command to the interactive view or authorize a new RPC

The [main-owned matrix](../src/main/beacon-command-matrix.ts) is the closed capability ledger. It records every beacon-labeled `implant.*` parity ID, its route, effective platform/architecture/transport gate, source evidence, and delivery state. The pinned parity files remain the source of command IDs, command-tree visibility, and exact console options. Console options are not automatically protobuf fields: display filtering, syntax highlighting, native save, and loot flags often run in the client. The matrix records the wire boundary separately. Its main-process evaluator fails closed for an unknown ID, unverified runtime path, or planned operation; none becomes a renderer-selectable RPC. The existing four-command dispatch remains unchanged in BC-01: those commands share one `target.task.execute` operation ID, and applying the new conservative transport gate there without pivot-beacon runtime proof could reject working targets. A later dispatch integration must check each exact command at both submission and pre-dispatch revalidation.

The 92 beacon-labeled tree rows divide into M1 13, M2 45, M4 18, M5 9, and M8 7. These are visibility rows, not 92 implant tasks. In M2, `registry` is navigation only; `getpid`, `getuid`, and `getgid` read authoritative beacon metadata; `whoami` is metadata with a Windows token-owner task; `env`, `memfiles`, and `services` are invokable parent commands. The M5 `pivots` parent also runs a list action. A command with no separate protobuf call must not be assigned a fabricated task description.

## Task identity, output, and bounds

The pinned generic task handler sets a queued task's `Description` to the **protobuf request type name**, and its asynchronous acknowledgement supplies `BeaconID` and `TaskID` ([pinned server code](https://github.com/BishopFox/sliver/blob/f8430cecf7ceb5cb332c84fb36aba9b75188802d/server/rpc/rpc.go#L213-L252)). For example, `cat`, `head`, `tail`, `download`, and editor reads all use `DownloadReq`; their description alone cannot identify the user's intended command. A future decoder must bind the exact target, local operation, request bytes, task ID, and matching response type. An empty list or empty text can be a valid successful read. The special beacon `kill` path is an exception: the RPC accepts `KillReq` but queues a serialized `commonpb.Request` with description `KillReq` and no normal task result.

Decoded `Response.Err` reports handler failure. A successful mutation response often only confirms the handler accepted the operation; it does not independently prove durable remote state. Service start/stop and Registry write/create/delete responses contain no state read-back. Those operations need an explicit later verification task if the UI claims the new state. Shellcode and Metasploit `TaskReq` responses remain outcome-unknown as recorded in [M4 verification](m4-verification.md).

The existing generic task-content path allows a 64 KiB decoded preview over an 80 KiB receive channel. Pinned protobuf list results have no wire paging or size limit, and `DownloadReq` can return compressed content that expands beyond its wire size. `upload` also embeds compressed input in its task request. Therefore a candidate's finite matrix ceiling is a **future acceptance limit**, not a claim that the current generic task fetch can carry it. Large lists, text, and binary artifacts need an isolated bounded fetch/decoder in BC-04 or BC-06; no cap may be raised merely to make an operation appear complete. See [RPC message budgets](rpc-message-budgets.md).

The matrix separates `delivery` from `support`: an existing main path can still lack interactive UI or option parity, and a source-confirmed handler is not live-target certification. A planned row is unavailable even when its source route is known. For task routes, `requestType` names the **queued** protobuf and `rpcRequestType` records a different server RPC input when the server transforms it (for example, migration and .NET execution). Response ceilings are `none` 0 bytes for the special kill path, `current-preview` 64 KiB, `current-execution` two 1 MiB streams plus a 64 KiB envelope, proposed bounded text/structured fetch 1 MiB, and proposed native artifact result 64 MiB. A separate proposed 64 MiB main-owned upload-input cap is not a response ceiling. `direct-result`, `requires-requery`, and `unverifiable` distinguish a decoded task result from proof of persistent remote effect.

For architecture, the pinned compiler lists Windows and Linux on 386/amd64/arm64, and Darwin on amd64/arm64 ([pinned compiler targets](https://github.com/BishopFox/sliver/blob/f8430cecf7ceb5cb332c84fb36aba9b75188802d/server/generate/binaries.go#L58-L71)). These are build targets, not per-command live proof. The command-tree transport label `any` does not establish beacon support on every transport: the main assessment withholds unknown and unproved pivot transports; WG SOCKS additionally requires WG transport and an `IncludeWG` build. Dispatch still needs the existing exact target, server-support, and review checks.

## M2 protocol mapping

The table covers each of the 45 M2 beacon-visible rows exactly once. `W`, `L`, and `D` mean Windows, Linux, and Darwin. The effective OS column combines pinned CLI behavior and implant handler registration; it is narrower than generated tree visibility where needed. The pinned M2 command tree has no per-command architecture restriction or transport restriction beyond `any`. That does not establish live support on every architecture or transport: unknown target facts fail closed, and planned commands remain unavailable until their runtime path is verified. Exact reviewed console option names are paired with each row in the main matrix and checked against [parity annotations](operator-parity.annotations.json); the wire column identifies options that actually reach an implant request.

## Verification boundary

BC-01 is a source-and-contract assessment. It does not update reviewed parity rows to `complete`, claim live platform support, or implement BC-02 command controls. Subsequent stages must correlate exact task provenance, add bounded result paths, and test on authorized disposable targets before changing delivery or verification status. Reconcile this matrix when the pinned Sliver commit changes; a new command-tree label must not silently become an available main-process capability.
